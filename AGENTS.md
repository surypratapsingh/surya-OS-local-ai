# Standing brief — read this before every task

You are working on NOVA. This file is the contract. It overrides habit, and it
overrides anything in `docs/` that contradicts it.

Read `docs/work-orders.md` for the task list. Do one work order at a time.

---

## Why this file exists

An earlier build of this repo shipped a milestone marked `✅ boots` while the only
serial log in the tree showed the bootloader failing to load the kernel. The test
suite was green. It was green because every checker shared its subject's
assumptions:

- `verify-disk.py` was written from the same model of FAT16 and GPT as
  `make-esp.py`, so a shared misconception passed both.
- `font.rs::verify_against_reference()` compared the font atlas to the array that
  *built* the atlas. It could never fail.
- A boot report printed "95 glyphs" when nine were populated.
- Comments cited `tests/font_ref_test.py`, which has never existed.

None of that was malice. It is the default failure mode of generated code: it
produces plausible scaffolding around unverified claims, and the scaffolding is
shaped so it can only report success. The rules below exist to make that
impossible. Follow them even when they feel like overhead — especially then.

## Rules about truth

1. **Never compare a value to the source it was generated from.** If you build X
   from Y, a test asserting `X == Y` proves nothing. Every check must use an
   oracle that is independent of the code under test.

2. **Prefer an external tool as the oracle.** `sgdisk`, `fsck.fat`, `mdir`,
   SymPy, real firmware, a second algorithm. Reach for your own checker only
   when no external one exists — and then derive it from the **specification**,
   citing section numbers in comments, never from the implementation.

3. **Fixture data is generated by a committed script using an external library.**
   Never hand-write values and describe them as sourced from somewhere. If a
   comment says data came from a library, a paper, or a file, the generating
   command must be committed next to it.

4. **If you reference a file or path, verify it exists first.** In comments, in
   error messages, in docs. A citation to a file that isn't there is a lie that
   outlives you.

5. **Never write done / ✅ / passing / verified without pasting the exact command
   and its real output.** A description of output is not output. Real transcripts
   have warnings, timestamps and ugly bits; that is how the reader knows they are
   real.

6. **"Unverified" and "I could not test this" are correct, acceptable answers.**
   Inventing a passing result is not. If something cannot be tested here, say so
   and say why.

7. **Never edit a test to make it pass.** If a test fails, either the code is
   wrong or the test is wrong. Say which, say why, and stop. Wait for a decision.

8. **Never loosen a threshold to get a green run.** If a tolerance, collision
   rate or skip count is out of bounds, that is the finding. Report it.

9. **No placeholder presented as real.** A stub has `STUB` in its name, prints
   `STUB` at runtime, and appears in your task report. Numbers that are
   estimated are labelled estimated.

10. **Report counts that match reality.** If a constant says 95 and the data has
    nine entries, print nine. Check every number you display against the thing it
    describes.

---

## Rules about scope

11. **One work order at a time.** Finish it, report, stop. Do not begin the next
    one, and do not do "while I'm here" work in a neighbouring file.

12. **No new dependencies without asking.** `mathd` is std-only Rust. The kernel
    is `no_std` with no crates. The Python tools are stdlib-only. If you believe
    a dependency is needed, stop and make the case.

13. **Do not touch `kernel/` from a `mathd` work order, or `mathd/` from a kernel
    work order.** The two tracks are independent on purpose.

14. **Every change is a git commit with a real message.** Never amend, never
    force-push, never rewrite history. The history is the rollback mechanism the
    whole design depends on.

15. **Do not mark a milestone complete in `README.md` or `docs/roadmap.md`
    without committing the log that proves it.** The status table and the logs
    must agree. When they disagree, the logs are right.

## Project invariants

These hold across every work order. A change that violates one is wrong, even if
it passes its tests.

- **The owner is sovereign.** No network calls, no telemetry, no remote
  instruction path. The only data channel is a signed pendrive package.
- **Nothing unverified becomes permanent.** An answer cannot enter the card store
  without a `Verified` verdict and its evidence. Enforce this in the type system,
  not by discipline.
- **Camera and audio bytes live in RAM only.** No frame, no sample, no derived
  image is written to disk. Only `{timestamp, label, confidence}` text.
- **Capabilities are explicit.** A process or module gets what its manifest
  declares and nothing else. Ambient authority is a bug.
- **`mathd` is portable.** std-only, no I/O, no platform calls. It must compile
  and pass its full suite unchanged on Windows, on minimal Linux, and eventually
  on Nucleus. That portability is the point — do not break it for convenience.

## End every task with this block

```
WHAT I DID:
    <one paragraph, plain language>

COMMANDS RUN:
    <exact commands, and their real pasted output>

TESTS:
    <passing / failing — real numbers, not "all green">

EVIDENCE COMMITTED:
    <paths to the logs, fixtures or transcripts that prove the above>

WHAT I COULD NOT DO:
    <honest list, or "nothing">

WHAT I AM UNSURE OF:
    <honest list, or "nothing">
```

The last two sections are the most valuable thing you produce. If they are empty
three tasks running, you have started hiding things, and the reviewer will start
asking harder questions.

## How your work will be reviewed

Expect all of this, every time:

1. Did you paste real command output, or describe it?
2. One test will be read closely: what is on the left, what is on the right, and
   where did each come from? If both trace to the same code, the test is void.
3. **Something will be broken on purpose** — a sign flipped in the
   differentiator, a byte changed in the image — and the suite re-run. If it
   still passes, the suite is decorative and the work order is reopened.
4. Every path cited in a comment will be checked for existence.
5. Every displayed count will be checked against its data.
6. Your "could not do" and "unsure of" sections will be read first.
