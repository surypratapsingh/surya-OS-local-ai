## Design Decisions

### Ed25519 Algorithm

**Why:** Mature EDDSA scheme standardized in RFC 8032. No fragility from key length choices (unlike RSA). Short signatures (64 bytes). Fast verification.

**Alternative considered:** RSA-2048. Rejected: larger keys/signatures, slower, more setup complexity.

### PKCS8 PEM Format

**Why:** Standard interchange format, supported by all modern crypto libraries, works on all platforms (Linux, macOS, Windows). Suitable for distributing public key only.

**Alternative considered:** OpenSSH format. Rejected: Python cryptography library requires extra handling; PKCS8 is simpler.

### Offline Key Storage

**Why:** Private key never present on network-connected machine. Eliminates class of attacks (network sniffing, malware exfiltration). Owner has full control.

**Options provided:**
1. Encrypted USB drive (portable, revocable)
2. Dedicated offline machine (maximum security)
3. Paper backup (disaster recovery)

### Reproducible Release Hash

**Why:** Same build inputs must produce byte-identical output. Signature covers only the hash, not the build process. Owner can verify the build independently.

**Implementation:**
- SHA256 of `build/nova.hdd` (no timestamps, no build paths in data)
- Committed at build time
- Transferred offline via USB

## Security Properties Achieved

✅ **Authenticity:** Owner signs all releases; cryptographic proof of origin  
✅ **Integrity:** Bit-level tampering detected (signature verification fails)  
✅ **Non-repudiation:** Owner's private key is proof of signature (barring key compromise)  
✅ **Replay protection:** Prepared in C2 (version counter + sequence numbers)  
✅ **Offline generation:** Private key never exposed to network

---

## Known Limitations

| Limitation | Impact | Mitigation |
|------------|--------|-----------|
| Private key compromise | All current and past releases become untrustworthy | Revoke public key immediately, generate new keypair, re-sign all releases |
| Owner signing a malicious release | All deployments become compromised | Social/organizational control; external review (D6) before release |
| USB drive with private key lost | Private key could be exposed (if passphrase known) | Assume exposure, revoke key immediately, generate new keypair |
| Signature verification skipped on install | Tampering in transit goes undetected | Enforce verification in C3 (installer must check signature before boot) |

---

## What This Is Not

This **does not**:
- Protect against physical tampering (see C6, Secure Boot)
- Protect against a compromised owner willingly signing bad code
- Protect against MITM attacks (transport security is separate concern)
- Provide key rotation automatically (owner must do this deliberately)

This **does** provide a clear, documented trust chain from owner to every installed bit of code.

## Next Steps (C2–C6)

**C2: Signed manifests** will take the public key from this phase and use it to verify:
- Manifest file listing (packages, versions, capabilities)
- Monotonic version counter (prevents rollback)
- Timestamp and signature

**C3: Atomic install** will verify the signature before handoff to any bootloader.

**C4: Extend signing** will sign the Limine bootloader and kernel using the same root key, unifying the trust chain.

**C5: Reproducible builds** will prove byte-identical images for given inputs (prerequisite for confident signing).

**C6: Secure Boot** will verify signatures at hardware level (optional; depends on threat model in D5).
